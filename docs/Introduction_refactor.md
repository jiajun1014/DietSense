## G. General — 領域大背景與現況

隨著全球飲食相關慢性病問題日趨嚴峻，體重管理與飲食自我監控的重要性已被大量實證研究確認。根據 WHO（2025）報告，全球超過 **10 億人口**處於肥胖狀態，飲食相關慢性病（糖尿病、心血管疾病、代謝症候群）佔全球死亡原因的 **74%**。台灣衛生福利部 2025 年國民健康訪問調查顯示，18 歲以上成人過重與肥胖合計比率達 **47.9%**，肥胖相關醫療支出每年逾新台幣 **500 億元**。

在工具面，全球健康飲食追蹤 App 市場規模已達 **68 億美元**（2025 年），年增率 17.4%，顯示社會對智慧飲食管理工具的強烈需求。Van Horn et al.（2024）的系統性回顧更確認，持續記錄飲食者平均比對照組多減輕 **3.3 公斤**，飲食追蹤的減重效益獲得 Level-I 實證支持。同期，大型語言模型（LLM）能力的快速提升，使「理解複雜自然語言描述並進行多步驟推理」在技術上首次成為可行，為對話式飲食追蹤 Agent 的實現提供了關鍵技術基礎。

## H. However — 深層技術與應用瓶頸

儘管飲食追蹤的效益已被充分驗證，然而 **85% 的使用者在 30 天內放棄**現有追蹤工具（Helander et al., 2014），核心原因在於傳統工具帶來的高認知負擔，具體表現為四大障礙：

**障礙一：資料庫搜尋負擔**
使用者必須從數萬至數十萬筆食物項目中精確搜尋名稱。現有工具（如 MyFitnessPal）資料庫雖逾百萬筆，但使用者需具備一定的食物命名知識才能有效搜尋，且台灣在地食物（夜市小吃、便當、傳統台菜）嚴重缺失或資料錯誤（Dhurandhar et al., 2015 指出錯誤率達約 30%）。

**障礙二：份量估算困難**
精確記錄份量通常需要磅秤，日常生活不可行。Poslusna et al.（2009）研究顯示，自報飲食攝取量平均**低估 18–54%**，份量不確定性是熱量計算誤差的最大來源。

**障礙三：複合料理拆解**
台灣常見的複合料理（如牛肉麵、便當、火鍋）需要使用者自行拆解為各食材再逐一查詢，需具備烹飪知識與耐心，使真實日常使用極為困難。

**障礙四：通用 LLM 的幻覺問題**
直接使用 ChatGPT 等通用 LLM 詢問食物熱量，系統可能捏造看似合理的數字，缺乏資料庫錨定，導致估算結果不可信賴且不可溯源。

## I. In Literature — 文獻發展梳理（舊到新，簡到繁）

飲食熱量追蹤的技術發展可分為三個世代：

**第一世代：手動資料庫 App（Rule-based Retrieval，2010–2020）**
以 MyFitnessPal（2010）、Cronometer 為代表，建立大型結構化食物資料庫供使用者手動搜尋記錄。優點是資料明確可溯源，缺點是操作繁瑣，資料庫維護品質參差不齊，且對台灣在地食物的覆蓋率極低。

**第二世代：電腦視覺食物辨識（CNN / Vision Transformer，2015–2023）**
以 Food-101 資料集訓練的 CNN 模型（EfficientNet-B4、ResNet-50）透過拍照自動辨識食物類別，再對應熱量資料庫。Cheng et al.（2024）的 EfficientNet 系統在標準資料集達 Top-5 準確率 89%，但無法處理份量估算、複合料理拆解與隱藏油脂問題。

**第三世代：LLM + Function Calling / RAG（2023–）**
隨著 GPT-4、LLaMA-3 的出現，研究者開始探索以 LLM 作為推理核心，透過 Function Calling 或 RAG 呼叫外部知識庫的 Agent 架構。Lin et al.（2024）的對話式食物記錄系統使記錄速度提升 3 倍；Wang et al.（2025）的 GPT-4 + RAG 系統在標準化飲食評估中達到 82% 準確率。這一典範的核心優勢在於以語意理解取代關鍵字搜尋，大幅降低使用者認知負擔。然而現有第三世代系統仍未整合台灣在地食物資料庫，且缺乏不確定性量化機制。

## J. Judgement — 各方法優劣點評析（SWOT 歸納）

| 方法類型 | 優點 | 缺點 | 適用情境 |
|---------|------|------|---------|
| 手動 App（MyFitnessPal）| 資料精確可溯源 | 操作繁瑣，台灣食物嚴重缺失 | 有高度動機的專業使用者 |
| 電腦視覺辨識（CNN）| 無需輸入，直觀 | 無法估算份量、隱藏油脂、複合料理 | 標準單一食物拍照情境 |
| 純 LLM（ChatGPT 等）| 理解自然語言 | 易幻覺，無資料庫錨定，不可溯源 | 概略估算，不適合精確追蹤 |
| 研究型硬體系統 | 高精確度 | 需特殊設備（3D 掃描、食物秤），無法日常部署 | 臨床研究環境 |
| **DietSense（本專題）** | **自然語言 + 資料庫錨定 + 台灣在地化 + 不確定性量化** | **純文字份量仍有估算誤差** | **日常對話式飲食追蹤** |

**核心觀察：**
現有技術各有其適用情境，但「日常可用 + 自然語言 + 資料庫可靠 + 台灣在地化 + 不確定性誠實量化」五者的交集，目前市場上尚無完整解決方案，形成明確的 Research Gap。

## K. Keypoint — 設計精神與核心貢獻

**設計精神：典範轉移**
從「使用者配合系統逐項填寫資料庫」→ 轉變為「AI Agent 理解日常語言並主動調度工具驗證」

**四大核心貢獻：**

1. **可運作的繁體中文對話式熱量追蹤 Domain AI Agent**
   結合 LLM Function Calling、台灣食品資料庫、Mifflin-St Jeor TDEE 計算引擎的完整端到端系統

2. **不確定性誠實量化機制**
   輸出熱量區間（低~高），基於信心分數動態調整估算邊界，避免偽精確單一數字誤導使用者

3. **台灣在地化飲食資料庫**
   覆蓋 60+ 台灣食物（夜市、便當、傳統台菜、手搖飲），填補現有西方為主系統的嚴重缺口

4. **飲食追蹤安全守門機制**
   偵測潛在飲食失調模式，於危險熱量限制情境下拒絕進一步限制建議，推薦諮詢專業營養師

**技術創新點：**
- 多來源資料庫 RAG 架構（台灣 DB → USDA → LLM 估算，依優先序）
- 信心分數門檻（≥ 80% 直接記錄；< 80% 觸發澄清問題，最多 1 個）
- SQLite 本地持久化，跨對話追蹤全天飲食
- OpenAPI 3.1 規格驅動開發（openspec.yaml），確保系統可驗證、可交接
